## ✨ 为什么 OpenClaw 用户需要超能力？

作为 OpenClaw 用户，你可能遇到过这些情况：

- ❌ 让 AI 助手创建一个 Skill，结果直接跳进去写代码，发现理解错了需求，全部重来
- ❌ 写了一半才发现漏了重要功能，返工
- ❌ 完成后测试发现一堆问题，修修补补又三天
- ❌ 文档写完没人看得懂，反复解释同样的问题

**超能力** 是一套专门为 OpenClaw 设计的创作工作流技能。它让你的 AI 助手在动手之前先思考，在写作之前先设计，在发布之前先验证。

**这是 OpenClaw 的"思考模式"** —— 让 AI 从"执行者"变成"创作者"。

---

## 🎯 超能力能做什么？

### 适合 OpenClaw 用户的场景

- ✅ **创建新的 OpenClaw Skill** - 从设计到发布的完整流程
- ✅ **撰写技术文档/教程** - 结构清晰、示例可运行、新手能看懂
- ✅ **设计工作方案/流程** - 先澄清需求，再制定计划，最后执行
- ✅ **创作系列内容** - 小红书文案、文章系列、教程连载
- ✅ **任何创意项目** - 需要设计和计划的创作工作

### 核心能力

| 能力 | 说明 | 价值 |
|------|------|------|
| 🧠 **需求澄清** | 通过问答澄清需求，提出多种方案 | 避免理解错误导致返工 |
| 📐 **设计优先** | 先设计后创作，分章节获得批准 | 确保方向正确 |
| 📋 **计划分解** | 分解为 2-5 分钟的小任务 | 降低复杂度，易于执行 |
| 🤖 **子代理执行** | 子代理逐任务执行 + 双重审查 | 高质量、快速迭代 |
| ✅ **测试驱动** | 先定义成功标准，再创作内容 | 确保内容真正满足需求 |
| 🔍 **内容审查** | 规范审查 + 质量审查 | 避免低级错误 |

## 🚀 快速开始

### 前提条件

- 已安装 [OpenClaw](https://openclaw.ai)
- OpenClaw 版本 >= 2026.3.8

### 安装超能力

在 OpenClaw 聊天窗口输入：

```
请安装超能力 skill，地址是 https://github.com/huichen/superpowers
```

OpenClaw 会自动克隆并安装技能。就这么简单！

### 开始使用

安装完成后，在 OpenClaw 聊天窗口直接说：

```
请用超能力技能帮我设计一个小红书文案生成工具
```

或者

```
请用超能力技能的需求澄清环节来规划这个文档
```

AI 助手会自动调用超能力工作流，带你走完整设计和计划流程。

## 💡 使用示例

### 示例 1：创建 OpenClaw Skill

```
你：请用超能力技能帮我创建一个飞书日历管理 Skill

AI: 好的！让我先用需求澄清环节来帮你设计。

首先，我想了解几个问题：
1. 这个 Skill 主要解决什么问题？
2. 目标用户是谁？
3. 需要支持哪些核心功能？
...

（经过问答澄清需求后）

AI: 基于我们的讨论，我设计了以下方案：

【设计方案】
- 核心功能：查询日程、创建会议、忙闲查询
- 技术实现：飞书日历 API + Bash 脚本
- 文件结构：SKILL.md + calendar.sh + templates/

你觉得这个设计如何？需要调整吗？
```

### 示例 2：撰写技术文档

```
你：请用超能力技能帮我写一篇技术教程

AI: 好的！在开始写作之前，让我先明确几个问题：

1. 目标读者是谁？（新手/专家）
2. 教程要解决什么问题？
3. 读者完成教程后能做什么？
4. 有什么前置知识要求？

...

（明确需求后）

AI: 我制定了以下写作计划：

【写作计划】
- 任务 1: 写简介和目标读者说明
- 任务 2: 写环境准备和安装步骤
- 任务 3: 写核心功能教程（含示例）
- 任务 4: 写故障排除和常见问题
- 任务 5: 写总结和下一步

每个任务都有明确的验证标准。我们开始第一个任务？
```

### 示例 3：内容审查

```
你：请用超能力技能帮我审查这篇文档

AI: 好的！我会从以下维度审查：

【审查维度】
1. 完整性 - 是否覆盖必要内容
2. 清晰度 - 读者能否理解
3. 一致性 - 术语、格式是否统一
4. 准确性 - 信息是否正确
5. 可用性 - 读者能否按说明操作

【审查结果】
✅ 优势：结构清晰、示例丰富
❌ 问题：
  - 关键：第 3 节示例无法运行（缺少必要参数）
  - 重要：术语不一致（Skill vs 技能混用）
  - 建议：添加故障排除部分

需要我帮你修复这些问题吗？
```

## 🎓 核心理念

### 测试驱动创作 (TDC)

传统创作：`创作 → 完成 → (可能) 检查 → 发布`

超能力方式：`定义成功标准 → 验证不满足 → 创作 → 验证满足 → 优化 → 发布`

**核心原则**：先定义什么是"完成"，再开始创作。

### 系统化而非临时

**临时创作的问题**：
- 想到哪写到哪
- 写完才发现漏了内容
- 读者问题层出不穷

**系统化的优势**：
- 先设计后创作
- 每步都有验证
- 问题在发布前发现

### 简洁性优先

**YAGNI 原则** - 坚决移除不必要的内容。

只创作当前需要的，不为未来可能的需求添加复杂度。

## 📊 对比

| 维度 | 普通 OpenClaw 助手 | 超能力 OpenClaw 助手 |
|------|-------------------|---------------------|
| 需求理解 | 直接执行，可能理解错 | 先问答澄清，确认理解 |
| 设计阶段 | 跳过设计，直接写 | 先设计，获得批准 |
| 计划分解 | 一步到位，复杂 | 分解为小任务，简单 |
| 质量保障 | 写完再看 | 每步验证，双重审查 |
| 返工率 | 高（30-50%） | 低（<10%） |
| 用户满意度 | 不稳定 | 稳定高 |

4. **测试驱动创作指南** - 实践 TDC 方法
5. **内容创作反模式** - 避免常见错误
