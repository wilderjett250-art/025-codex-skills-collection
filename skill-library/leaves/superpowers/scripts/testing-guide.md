# 测试驱动创作指南 (Test-Driven Creation)

**版本**: 1.0.0  
**适用**: Skill 创作、文档撰写、方案设计等创意项目

---

## 🎯 什么是测试驱动创作？

测试驱动创作 (TDC) 是将测试驱动开发 (TDD) 的理念应用于内容创作的方法。

**核心原则**：先定义成功标准，再创作内容。

```
RED → GREEN → REFACTOR
```

1. **RED** - 定义成功标准，验证当前不满足
2. **GREEN** - 创作最小内容让标准满足
3. **REFACTOR** - 优化内容，保持质量

---

## 📋 为什么需要 TDC？

### 传统创作的问题

```
创作 → 完成 → (可能)检查 → 发布
```

**问题**：
- 写完才发现漏了重要内容
- 读者说"看不懂"但为时已晚
- 示例无法实际运行
- 文档与实际功能不符

### TDC 的方式

```
定义成功标准 → 验证不满足 → 创作 → 验证满足 → 优化 → 发布
```

**优势**：
- 创作前就清楚什么是"完成"
- 每部分内容都经过验证
- 读者问题在发布前发现
- 文档与功能保持一致

---

## 🔧 如何应用 TDC

### 步骤 1: 定义成功标准 (RED)

**在创作任何内容之前**，先定义什么是"完成"。

**好的成功标准**：
- ✅ 具体 - 明确说明要什么
- ✅ 可验证 - 能检查是否满足
- ✅ 简洁 - 一条标准一个点

**示例（Skill 创作）**：

```markdown
## 成功标准

- [ ] SKILL.md 头部包含 name 和 description 字段
- [ ] 至少有 1 个可执行的命令
- [ ] 包含使用方法示例
- [ ] 新用户能独立使用 Skill
- [ ] 所有示例命令都能实际运行
```

**不好的成功标准**：
- ❌ "文档要写好" - 不具体
- ❌ "内容要完整" - 不可验证
- ❌ "用户能看懂" - 太模糊

### 步骤 2: 验证当前不满足 (Verify RED)

**确认测试真的会失败**。

```bash
# 检查文件是否存在
ls -la SKILL.md

# 检查是否有所需字段
grep "^name:" SKILL.md

# 运行示例命令
./script.sh --help
```

**预期**：失败（因为还没创作）

**如果测试通过**：说明内容已存在，重新评估是否需要创作。

### 步骤 3: 创作最小内容 (GREEN)

**只创作让测试通过所需的最少内容**。

**示例**：
- 要测试"name 字段存在" → 只写 `name: xxx`
- 要测试"命令可执行" → 只写最小可运行脚本
- 要测试"有使用示例" → 只写 1 个最简单的示例

**不要**：
- 添加额外功能
- 提前优化
- 写"可能有用"的内容

### 步骤 4: 验证满足 (Verify GREEN)

**确认内容真的满足标准**。

```bash
# 重新运行验证
grep "^name:" SKILL.md  # 应该找到
./script.sh --help      # 应该显示帮助
```

**预期**：所有测试通过

**如果失败**：修复内容，不是修改测试。

### 步骤 5: 优化 (REFACTOR)

**在测试通过后才优化**。

**优化内容**：
- 改进标题和结构
- 增加更多示例
- 改善语言表达
- 统一术语和格式

**保持**：
- 所有测试仍然通过
- 不添加新功能

### 步骤 6: 重复

下一个成功标准，回到步骤 1。

## 📝 Skill 创作测试清单

### 结构测试

```markdown
- [ ] SKILL.md 存在
- [ ] 头部有 name 字段（格式：`name: xxx`）
- [ ] 头部有 description 字段
- [ ] 有目录结构说明
- [ ] 有使用方法
- [ ] 有配置说明（如需）
- [ ] 有更新日志
```

### 功能测试

```markdown
- [ ] 主脚本存在且可执行
- [ ] `--help` 命令显示帮助
- [ ] 至少 1 个功能命令可运行
- [ ] 错误处理正常（无效参数有提示）
- [ ] 输出清晰易懂
```

### 文档测试

```markdown
- [ ] 新用户能独立使用（找不认识的人测试）
- [ ] 所有示例命令都能运行
- [ ] 配置步骤清晰可跟随
- [ ] 故障排除部分覆盖常见问题
- [ ] 术语一致（全文统一用词）
```

### 模板测试

```markdown
- [ ] 模板文件存在
- [ ] 模板有清晰的占位符标记
- [ ] 用示例数据填充模板有效
- [ ] 模板输出符合预期格式
```

### 提示词测试

```markdown
- [ ] 提示词文件存在
- [ ] AI 能理解提示词（调用测试）
- [ ] 生成内容质量合格（人工审查）
- [ ] 边界情况处理正常（空输入、异常输入）
```

## 🎯 内容质量检查清单

### 简洁性

- [ ] 没有冗余内容
- [ ] 每段有单一主题
- [ ] 没有"可能有用"的内容
- [ ] 删除了不必要的解释

### 清晰度

- [ ] 标题准确反映内容
- [ ] 段落简短（<200 字）
- [ ] 列表用于多项内容
- [ ] 示例具体可操作

### 一致性

- [ ] 术语统一（Skill vs 技能）
- [ ] 格式统一（标题级别、列表样式）
- [ ] 语气一致（正式/非正式）
- [ ] 代码风格统一

### 完整性

- [ ] 覆盖所有必要内容
- [ ] 有使用示例
- [ ] 有故障排除
- [ ] 有版本记录

### 准确性

- [ ] 所有示例可运行
- [ ] 所有命令经测试
- [ ] 所有链接有效
- [ ] 所有信息最新

## 🐛 常见问题

### Q: 定义成功标准太花时间

**A**: 花 2 分钟定义标准，节省 20 分钟返工。

从简单的开始：
- "文件存在"
- "命令可运行"
- "示例能执行"

熟练后再添加更细致的标准。

### Q: 有些内容不好定义测试

**A**: 用检查清单代替自动化测试。

例如"语言流畅"不好自动化测试，但可以：
- [ ] 大声朗读一遍，没有卡顿
- [ ] 找其他人阅读，没有疑问
- [ ] 没有长句（>50 字）

### Q: 测试太多，创作变慢

**A**: 测试是为了更快，不是更慢。

如果测试让你变慢：
- 测试可能太细（合并一些）
- 测试可能不可验证（简化）
- 可能不需要这个测试（删除）

**好的测试**：帮助你不返工  
**坏的测试**：为了测试而测试

### Q: 创作到一半发现标准不对

**A**: 正常！修改标准，继续。

测试驱动是迭代过程：
1. 定义标准
2. 发现标准不对
3. 修改标准
4. 继续创作

这比写完才发现好得多。

## 📚 示例：创作 Skill 的 TDC 过程

### 迭代 1: 基础结构

**成功标准**：
- [ ] SKILL.md 文件存在
- [ ] 有 name 字段
- [ ] 有 description 字段

**RED**: 文件不存在 → 失败 ✅

**GREEN**: 创建 SKILL.md，写头部

```markdown
---
name: my-skill
description: 我的技能
---
```

**Verify GREEN**: 文件存在，字段有 → 通过 ✅

**REFACTOR**: 无（太早）

### 迭代 2: 功能脚本

**成功标准**：
- [ ] 主脚本存在
- [ ] 脚本可执行
- [ ] `--help` 显示帮助

**RED**: 脚本不存在 → 失败 ✅

**GREEN**: 创建 script.sh

```bash
#!/usr/bin/env bash
case "${1:-}" in
  --help) echo "使用方法：./script.sh [命令]" ;;
  *) echo "未知命令" ;;
esac
```

**Verify GREEN**: 
```bash
chmod +x script.sh
./script.sh --help  # 输出：使用方法：./script.sh [命令]
```
通过 ✅

**REFACTOR**: 添加颜色输出、错误处理

### 迭代 3: 文档完善

**成功标准**：
- [ ] 有使用方法部分
- [ ] 至少 1 个示例
- [ ] 示例可运行

**RED**: 没有使用方法 → 失败 ✅

**GREEN**: 添加到 SKILL.md

```markdown
## 使用方法

```bash
# 查看帮助
./script.sh --help

# 运行命令
./script.sh my-command --arg value
```
```

**Verify GREEN**: 
```bash
# 运行示例
./script.sh --help  # ✅
./script.sh my-command --arg value  # ✅
```
通过 ✅

**REFACTOR**: 添加参数说明表格、更多示例

### 迭代 4: 用户测试

**成功标准**：
- [ ] 新用户能独立使用
- [ ] 没有未解答的问题

**RED**: 找不认识的人测试 → 发现问题 ✅

**GREEN**: 根据反馈补充文档

- 添加配置说明
- 添加故障排除
- 添加常见问题

**Verify GREEN**: 新用户再次测试 → 通过 ✅

**REFACTOR**: 优化结构、改进表达

---

## 🎯 记住

**测试驱动创作不是关于测试，是关于思考。**

在创作之前思考：
- 什么是"完成"？
- 如何验证？
- 读者需要什么？

这比写完再改高效得多。
